# HW05. Темпоральные спецификации и проверка моделей

## 1. Цель работы

Цель работы — описать конечную модель протокола «запрос — ответ», сформулировать свойства безопасности и живости в темпоральной логике CTL и проверить их с помощью NuSMV. По результатам проверки требуется объяснить истинные и ложные свойства и разобрать контрпример.

## 2. Выбор модели и допущения

Рассматривается упрощённый протокол взаимодействия клиента и сервера. Клиент отправляет запрос, после чего система может либо выдать ответ, либо остаться в состоянии ожидания ответа.

Используются четыре состояния:

| Состояние | Значение |
|---|---|
| `idle` | Система ожидает новый запрос |
| `req` | Запрос отправлен, ожидается ответ |
| `ack` | Ответ получен |
| `error_state` | Ошибочное состояние |

Начальное состояние — `idle`. Переходы:

| Текущее состояние | Возможные следующие состояния |
|---|---|
| `idle` | `req` |
| `req` | `req` или `ack` |
| `ack` | `idle` |
| `error_state` | `error_state` |

Модель конечная и недетерминированная: из `req` возможны два перехода. Повторный переход `req → req` означает, что ответ задерживается. Состояние `error_state` включено в модель для проверки свойства безопасности, но из начального состояния недостижимо. Предположения о справедливости (fairness) не задаются. Поэтому модель допускает бесконечное выполнение `req → req → ...`.

## 3. Переменные и атомарные предикаты

| Обозначение | Смысл |
|---|---|
| `state` | Текущее состояние автомата |
| `request` | Истинно, если `state = req` |
| `response` | Истинно, если `state = ack` |
| `waiting` | Истинно, если `state = idle` |
| `error` | Истинно, если `state = error_state` |

Переменная `state` принимает одно из четырёх перечисленных значений. Так как используется одна перечислимaя переменная, два разных состояния не могут быть активны одновременно.

## 4. Проверяемые свойства

В NuSMV используются CTL-формулы. Обозначения: `AG` — на всех путях во всех состояниях; `AX` — во всех следующих состояниях; `AF` — на всех путях когда-нибудь в будущем; `EF` — существует путь, на котором когда-нибудь выполняется условие.

### Свойства безопасности

| № | Требование | Формула |
|---|---|---|
| S1 | Запрос и ответ не могут быть активны одновременно | `AG !(request & response)` |
| S2 | После получения ответа система переходит в ожидание | `AG (response -> AX waiting)` |
| S3 | Из состояния ожидания система переходит к отправке запроса | `AG (waiting -> AX request)` |
| S4 | Если система попала в ошибочное состояние, она остаётся в нём | `AG (error -> AX error)` |

Свойства безопасности запрещают нежелательные состояния или переходы. Нарушение такого свойства можно было бы показать конечным префиксом трассы, достигающим запрещённой ситуации.

### Свойства живости

| № | Требование | Формула |
|---|---|---|
| L1 | Каждый отправленный запрос в конечном итоге получает ответ | `AG (request -> AF response)` |
| L2 | Существует сценарий, в котором система получает ответ | `EF response` |

L1 — универсальное требование: ответ должен прийти при любом допустимом продолжении выполнения. L2 — экзистенциальное требование: достаточно существования хотя бы одного пути к ответу. Эти свойства различаются по смыслу.

## 5. Результаты проверки

Ожидаемые результаты проверки модели:

| Свойство | Результат | Обоснование |
|---|---|---|
| S1 | TRUE | `request` и `response` соответствуют разным значениям одной переменной `state` |
| S2 | TRUE | Единственный переход из `ack` ведёт в `idle` |
| S3 | TRUE | Единственный переход из `idle` ведёт в `req` |
| S4 | TRUE | Для `error_state` задан переход только в само себя |
| L1 | FALSE | Из `req` разрешено бесконечно переходить обратно в `req` |
| L2 | TRUE | Существует путь `idle → req → ack` |

Таким образом, четыре свойства безопасности выполняются, а универсальное требование об обязательном получении ответа нарушается. При этом ответ достижим хотя бы в одном сценарии.

## 6. Контрпример для свойства L1

Для формулы `AG (request -> AF response)` NuSMV должен обнаружить путь, на котором запрос отправлен, но ответ никогда не приходит.

Контрпример:

```text
s0: idle
 |
 v
s1: req
 |
 v
s1: req
 |
 v
s1: req
 |
 v
... повторяется бесконечно
```

После перехода в `req` система каждый раз выбирает переход `req → req`. Состояние `ack` не достигается. Следовательно, требование «каждый запрос когда-нибудь получает ответ» нарушается.

Это не ошибка NuSMV и не обязательно ошибка реализации модели: такой сценарий прямо разрешён заданными переходами. Он показывает, что в модели нет гарантии своевременного ответа.

## 7. Свидетельство истинности L2

Формула `EF response` истинна, поскольку существует путь:

```text
idle → req → ack
```

На этом пути состояние `ack` достигается за два перехода. Для экзистенциальной формулы достаточно одного такого пути; проверять все возможные пути не требуется.

## 8. Воспроизводимость

Файл модели: `request_response.smv`.

Для проверки необходим установленный NuSMV или совместимый nuXmv. Запуск из командной строки:

```bash
NuSMV request_response.smv
```

Модель не использует внешние данные, случайные параметры или дополнительные процессы. Все состояния и переходы заданы непосредственно в SMV-файле.

## 9. Вывод

В ходе работы была построена конечная модель протокола «запрос — ответ» и сформулированы четыре свойства безопасности и два свойства живости в CTL. Проверка показывает, что все заданные свойства безопасности выполняются. Свойство существования пути к ответу также выполняется, однако универсальная гарантия получения ответа нарушается.

Контрпример демонстрирует бесконечное повторение состояния ожидания ответа. Следовательно, для обеспечения живости необходимо изменить модель: например, исключить бесконечное ожидание или ввести дополнительное условие, гарантирующее переход от `req` к `ack`.
